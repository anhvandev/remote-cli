# 22: Windows: SYSTEM service, self-installing exe, lock/login/UAC

**What to build:** Replaces `.scratch/remote-cli/issues/29`. Double-clicking `rcli.exe` opens the GUI with an Install button (Server Address + Key). The PowerShell one-liner (`install.ps1`, finished here) and `rcli agent install` in an elevated shell also work. Install copies the binary, records the Terminal User, registers the Device, and installs a SYSTEM service that launches a helper in the active console session using the winlogon token. The helper switches to the input desktop before capture and input and rebuilds capture on desktop changes, so the lock screen, login screen and UAC prompts can be observed and controlled. Ctrl+Alt+Del is sent with SendSAS. The Secret Store uses DPAPI (machine scope). Uninstall removes everything. The build is unsigned, so the guide page covers SmartScreen. See `.scratch/easy-setup/spec.md`.

  Checked from macOS only: everything cross-compiles and clippy is clean, but **nothing has run on Windows yet**.

  **What was built**

  - `crates/cli/src/windows_install.rs` — the installer, modelled on `macos_install.rs`: a `Layout` (binary at
    `%ProgramFiles%\rcli\rcli.exe`, data at `%ProgramData%\rcli`), `install_files`/`install_service`/
    `uninstall_files` through a `Run` seam, and a `ServiceConfig` JSON that holds the Server Address and Server Key.
    The key is **not** on the service's command line (it goes to `%ProgramData%\rcli\service.json`, ACL'd with
    `icacls /inheritance:r /grant:r *S-1-5-18:F *S-1-5-32-544:F`, so `sc qc rcli-agent` and the registry show no
    key). Registration happens before the service is created, so a wrong Server Key fails the install and removes
    what was written; on success it prints the Device ID and Device Password. The Terminal User is the console
    user (`WTSQuerySessionInformationW`), not the elevated admin account, and is stored in Device Settings.
  - `crates/cli/src/windows_service.rs` — the service host with the `windows-service` crate (v0.8.1): the SCM
    dispatcher reports StartPending → Running → Stopped, so the process no longer dies with 1053. It reads
    `service.json`, starts the session watcher, and runs the Agent on a worker thread with its own tokio runtime.
    Logs go to `%ProgramData%\rcli\agent.log` (a service has no console). Started from a shell (not the SCM) it runs
    the same code in the foreground for debugging.
  - `crates/agent/src/session.rs` + `windows_session.rs` — the daemon ↔ helper split now shares its protocol and
    `SessionPlatform` between macOS and Windows. The Windows service launches `rcli agent session --pipe …` in the
    active console session with a SYSTEM token moved into it (`DuplicateTokenEx` +
    `SetTokenInformation(TokenSessionId)` with `SeTcbPrivilege`; `WTSQueryUserToken` is the fallback). That is the
    token winlogon runs with there, which is what may open the `Winlogon` and UAC secure desktops. A watch thread
    polls the console session and relaunches the helper on logon/logoff/user change/crash (a service has no message
    loop for `WTSRegisterSessionNotification`). The helper opens the input desktop (`OpenInputDesktop` +
    `SetThreadDesktop`) before every capture, input and UI Automation call, so lock, sign-in and UAC are observable
    and controllable. Displays, capture, input, accessibility, session state and Lock go to the helper; shell,
    power, metrics, inventory and processes stay in the service. Transport: the named pipe
    `\\.\pipe\rcli-agent-session` with a DACL that admits SYSTEM, Administrators and other local users.
  - Ctrl+Alt+Del: `Input::Sas` in the Platform port, produced by `rcli act <id> key ctrl+alt+del` (the Executor
    recognizes the combination in any spelling/order) and sent with `SendSAS(FALSE)` from the SYSTEM helper.
  - DPAPI: `DpapiSecretStore` in `crates/agent/src/secret_store.rs` (`CryptProtectData`/`CryptUnprotectData` with
    `CRYPTPROTECT_LOCAL_MACHINE`, the secret name as entropy), wired into `crate::agent::secret_store` on Windows.
  - GUI: the Install form now shows on Windows too; `elevated()` runs `rcli` through `cmd.exe` after a UAC prompt
    and returns its output, so reveal/change/settings work elevated as on macOS/Linux.
  - `install.ps1` (generated by `crates/server/src/api/install.rs`) now downloads and, when not already elevated,
    relaunches itself through UAC and waits for the exit code. `install.sh` comment updated.
  - `rcli agent uninstall` stops and deletes the service and removes `%ProgramFiles%\rcli` and `%ProgramData%\rcli`
    (credentials, Device Settings, DPAPI blobs), so nothing is left behind.
  - `rcli upgrade` on an installed Agent restarts the service through `sc.exe` instead of spawning a child outside
    the SCM.
  - `rcli-testkit` builds on Windows now: the trusting IPC variant exists for named pipes too, and the truly
    Unix-only tests (`socket modes`, SIGTERM, devstack) are gated, so `cargo xwin clippy --workspace --all-targets`
    is clean.

  **Shortcuts taken** (each marked `shortcut:` in the code)

  - The helper runs as SYSTEM in the console session, not as the logged-in user: a user token cannot open the
    `Winlogon`/secure desktops, which the ticket needs for lock, login and UAC. Consequence to check on real
    hardware: WinRT OCR runs under SYSTEM, so `--text` targeting at the lock screen needs an OCR language available
    to the SYSTEM profile (UI Automation is also unavailable there, so OCR is the fallback).
  - The session watch is a 2 s poll, not `WTSRegisterSessionNotification` (that needs a window and a message loop).
  - The named-pipe helper channel has no read timeout, unlike the macOS socket; a hung helper would block an Agent
    call. The helper is our own process and the watcher restarts it when it exits.
  - A SYSTEM service cannot put the GUI window on the console user's desktop without an extra `CreateProcessAsUser`
    round trip. Until that exists, prompts that need the GUI at the Device (root `ask`, `password+accept`) reject on
    Windows because nobody can answer them; `rcli agent root always` / `accept password` work.
  - `shell`/`pty` still run as the account the Agent runs as (SYSTEM in the service), not as the Terminal User; the
    ticket-21 shortcut stands until ticket 26.
  - `install.ps1` puts the Server Key on the installer's own command line (unavoidable for `--key`, visible only
    while installing); the *service* never sees it on a command line. The script also does not unblock the
    downloaded exe: SmartScreen may ask once (guide page/ticket 38 covers this).
  - No Start Menu shortcut is created; the Dashboard's one-liner and `rcli.exe` are the entry points.
  - The contract suite cannot run in the service's context: it constructs a Platform in the caller's session. The
    lock/login/UAC acceptance check below therefore uses a Controller against the installed service.

  **To run on a real Windows 10/11 machine** (all PowerShell; `rcli.exe` means the cross-built
  `target/x86_64-pc-windows-msvc/debug/rcli.exe` or a release build; replace `SERVER` with `host:port` from the
  Dashboard's Connect page and `KEY` with the Server Key)

  ```powershell
  # A. Elevated CLI install. In PowerShell "Run as administrator":
  .\rcli.exe agent install --server SERVER --key KEY
  # Expect: "installed C:\Program Files\rcli\rcli.exe and started the service rcli-agent", a 9-digit Device ID and
  # a 10-character Device Password. Then:
  Get-Service rcli-agent            # Status Running, StartType Automatic
  sc.exe qc rcli-agent              # has agent service --config ... ; NO rk_ key anywhere
  Get-Content "$env:ProgramData\rcli\service.json"   # works elevated; icacls shows only SYSTEM/Administrators
  rcli.exe agent info               # device id + connected
  # Wrong key must fail without leaving a service:
  .\rcli.exe agent install --server SERVER --key rk_00_bad
  # Expect an error mentioning the Server Key/registration; Get-Service rcli-agent then fails (absent), and
  # %ProgramFiles%\rcli was removed.

  # B. One-liner (normal, non-elevated PowerShell):
  iwr http://SERVER_DASHBOARD/install.ps1 -OutFile install.ps1
  .\install.ps1 -Key KEY
  # Expect a UAC prompt, then the same Device ID/password output, exit code 0.

  # C. GUI: log in as a normal user, double-click rcli.exe. The rcli window opens with Server Address and Server
  # Key fields and an Install button (because no Agent answers). Fill them, click Install, accept UAC.
  # Expect the note to show the Device ID/password, and Get-Service rcli-agent to be Running.

  # D. Reboot survival:
  Restart-Computer
  # After logging in again: Get-Service rcli-agent -> Running; rcli.exe agent info -> connected; the Dashboard
  # shows the Device Online without anyone starting it.

  # E. Lock / sign-in / UAC, from a Controller machine with rcli setup + rcli connect <Device ID>:
  rcli lock acquire <Device ID>
  rcli shot <Device ID> --out .\shots          # while locked
  # On the Windows box press Win+L; expect a screenshot of the lock screen (clock/background).
  rcli act <Device ID> type "..." --observe none   # or click the sign-in field / press a key
  # Sign out (or restart and stay at the login screen): rcli shot <Device ID> shows the sign-in screen, and
  # rcli act <Device ID> key ... / click works there.
  # Trigger any UAC prompt (e.g. run "regedit" as a standard user): while the secure desktop is up,
  # rcli shot <Device ID> shows the UAC dialog dimmed background, and rcli act <Device ID> click ... can hit
  # "No"/"Yes" only if the Controller has root rights on that Device (Device Settings root).
  # Expect session state in `rcli device show`: LockScreen / LoginScreen / Active.

  # F. Ctrl+Alt+Del (one time, elevated):
  Set-ItemProperty -Path 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System' `
    -Name SoftwareSASGeneration -Type DWord -Value 1
  # Then from the Controller: rcli act <Device ID> key ctrl+alt+del
  # Expect the Windows security screen (Lock / Switch user / Sign out / Task Manager). With SoftwareSASGeneration
  # 0 (default) nothing happens: that is the documented policy requirement (docs/usage.md).

  # G. Unlock at the lock and sign-in screens (elevated on the Windows box, once):
  rcli.exe agent unlock-password set     # type the Windows account password + Enter
  # From the Controller: rcli unlock <Device ID> --out .\shots
  # Expect the typed password + Enter to unlock at the lock screen and to sign in at the login screen, and the
  # returned shot to show the desktop. `rcli agent unlock-password clear` removes it.

  # H. Uninstall (elevated):
  rcli.exe agent uninstall
  # Expect "stopped and deleted the service rcli-agent; removed C:\Program Files\rcli\rcli.exe ...".
  Get-Service rcli-agent      # fails: the service is gone
  Test-Path "$env:ProgramData\rcli"   # False
  # The Device is removed from the Server by the uninstall itself (ticket 16's self-removal; an unreachable
  # Server is a warning and the local uninstall still finishes). An Admin can still delete it with `rcli device delete`.
  ```
